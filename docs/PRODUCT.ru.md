## Цель

Пользователь получает один самостоятельный продукт без зависимости от старого `Olcrtc_manager`:

- сервер olcRTC и Web UI на Debian 12 VPS;
- клиент olcRTC и Web UI на Keenetic с Entware ARM64;
- настройка обычного сценария только через браузер;
- единый Spec URI и QR для переноса конфигурации с VPS на Keenetic;
- диагностика, обновление, откат, резервная копия и удаление из Web UI;
- две короткие команды для чистой установки после публикации release.

Редактирование YAML вручную остаётся аварийным режимом и не требуется для обычной работы.

## Источники и обновляемость

Ядро форка сохраняет официальный upstream `openlibrecommunity/olcrtc`. Коммиты upstream регулярно подмешиваются в `master`, а платформенные изменения находятся в `packaging/`, `web/` и административном backend. Release обязан записывать точный upstream commit.

UX и функции прежнего Manager изучаются по `Oleglog/Olcrtc_manager`. Его WTFPL v2 разрешает копирование и изменение. В форк переносится только нужная панель и логика управления, без встроенных бинарников, временных файлов и старых конфликтующих unit. Происхождение указывается в `THIRD_PARTY.md`.

## Имена и владение файлами

Продукт использует единый namespace `olcrtc-native`.

### Debian

- бинарник: `/usr/local/lib/olcrtc-native/current/olcrtc`;
- панель: `/usr/local/lib/olcrtc-native/current/olcrtc-admin.py`;
- конфигурация: `/etc/olcrtc-native`;
- состояние и резервные копии: `/var/lib/olcrtc-native`;
- службы: `olcrtc-native-admin.service` и `olcrtc-native@<instance>.service`;
- Web UI: `https://0.0.0.0:8443` с обязательным TLS.

### Keenetic Entware

- бинарник: `/opt/lib/olcrtc-native/current/olcrtc`;
- конфигурация: `/opt/etc/olcrtc-native`;
- состояние и резервные копии: `/opt/var/lib/olcrtc-native`;
- службы: `S96olcrtc-native` и `S97olcrtc-web`;
- Web UI: `http://<LAN-IP>:8091`, только RFC1918 IPv4.

Ни сервер, ни клиент не создают правило WAN автоматически.

## Полный пользовательский сценарий

1. Пользователь запускает одну команду на VPS от `root`.
2. Установщик проверяет ОС, архитектуру, место, DNS, TLS и release manifest.
3. Если найдена старая установка, создаётся архив конфигурации и служб. До явного выбора в UI старая служба не удаляется.
4. Установщик показывает URL панели и путь к одноразовым первичным данным входа.
5. В панели пользователь создаёт инстанс. Безопасные room, key и client ID генерируются автоматически.
6. Панель проверяет конфигурацию, запускает сервер и показывает готовность, Spec URI и QR.
7. Пользователь запускает одну команду на Keenetic.
8. Панель Keenetic открывается даже без клиентской конфигурации. Пользователь вставляет Spec URI или сканирует QR на другом устройстве.
9. Клиент проверяет совместимость и запускается сначала только как локальный SOCKS5 `127.0.0.1:8808`.
10. Сквозная проверка подтверждает DNS, HTTPS и внешний IP VPS. Только после этого продукт предлагает удалить старую установку.

## VPS Web UI

### Главная

- IP, ОС, uptime, release, upstream commit, TLS и состояние обновлений;
- число инстансов, активных соединений и последняя успешная проверка;
- карточки инстансов со статусом, provider, transport, room, uptime и трафиком;
- кнопки запуска, остановки, перезапуска, проверки, клонирования и удаления;
- предупреждения показывают действие для исправления, а не только текст ошибки.

### Мастер инстанса

- имя и необязательное описание;
- provider: Jitsi, Telemost, WB Stream;
- transport только из совместимых вариантов;
- room URL с проверкой синтаксиса и доступности;
- client ID, key и параметры transport с безопасной автогенерацией;
- DNS, liveness, reconnect и traffic shaping;
- базовый и экспертный режим формы;
- предпросмотр без секретов и проверка до записи;
- атомарное применение с автоматическим возвратом предыдущего YAML при неудачном старте.

Jitsi `room=any` запрещён. Для Jitsi требуется `https://host/room` или `host/room`. Несовместимая пара provider/transport блокируется до записи файла.

### Подключение клиента

- canonical Spec URI скрыт по умолчанию;
- явное раскрытие на короткое время;
- одноразовый QR;
- копирование URI;
- подписка `/sub/<slug>`;
- отзыв и перевыпуск ключа;
- секреты не появляются в списках, URL панели и журналах.

### Управление

- журналы сервера и панели с redaction;
- диагностика DNS, времени, provider, портов, файлов, systemd и release;
- проверка обновлений, точный release, latest, прогресс, перезапуск и rollback;
- резервная копия, восстановление и скачивание диагностического отчёта без секретов;
- смена логина/пароля, завершение всех сессий, TLS-сертификат и домен;
- импорт старой установки, тестовое переключение и отдельное окончательное удаление;
- полное удаление продукта только после создания recoverable backup.

Опциональные FreeDNS, собственный домен, Yandex Disk mirror и WB Chromium оформляются отдельными модулями. Неподдерживаемый модуль не должен мешать основной работе.

## Безопасность

- пароль хранится как salted scrypt hash;
- VPS использует `Secure`, `HttpOnly`, `SameSite=Strict` cookie;
- каждый изменяющий запрос требует сессию, CSRF и допустимый Origin;
- вход имеет rate limit, сессии имеют срок и могут быть отозваны;
- backend выполняет только фиксированные команды и не подставляет ввод пользователя в shell;
- имена, URL, enum, числа и пути проверяются по allowlist;
- временные файлы получают безопасные права и заменяются атомарно;
- secret, key, URI, password и token удаляются из ответа и журналов;
- обновление принимает только asset из строгого manifest с repository, release, size и SHA-256;
- удаление разрешено только для перечисленных путей `olcrtc-native`;
- очистка старого Manager никогда не запускается по умолчанию.

## Чистая установка и удаление старого

Режим `fresh` выполняет следующие фазы:

1. обнаружение `olcrtc-admin.service`, `olcrtc-server.service`, `olcrtc-server@.service`, `/etc/olcrtc`, старых Entware init-скриптов и владельца порта `8808`;
2. архив в отдельном каталоге с manifest и контрольными суммами;
3. остановка только обнаруженных olcRTC-служб;
4. установка `olcrtc-native`;
5. проверка Web UI и тестовый запуск;
6. только после явного `purge-legacy` удаление точного списка старых файлов;
7. при любой ошибке восстановление unit, конфигурации и состояния запуска.

Нельзя использовать широкие маски, удалять `/etc/olcrtc*`, `/opt/etc/init.d/S*olcrtc*` или каталоги, не записанные в backup manifest.

## Единая модель ошибок

Каждая операция возвращает:

- стабильный код ошибки;
- русское описание;
- этап;
- безопасную техническую деталь;
- действие для исправления;
- `retryable`;
- идентификатор записи журнала.

UI не считает PID достаточным признаком готовности. Для сервера проверяется systemd и конфигурация, для клиента дополнительно SOCKS5 и сквозной HTTPS-запрос.

## Правило выпуска

Предварительный release публикуется только после зелёных CI и тестов чистой установки в виртуальной Debian-среде. Стабильный release дополнительно требует реального Keenetic ARM64, перезагрузки обеих сторон, сквозного SOCKS5-теста, проверки обновления, rollback и отсутствия WAN-доступа к панели роутера.
