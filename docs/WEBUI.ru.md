# Панели управления форка

Документ определяет готовый пользовательский сценарий. Ручное редактирование YAML остаётся аварийным и экспертным способом, но не требуется для обычной установки.

## Общая схема

1. Панель VPS создаёт серверный инстанс и атомарно записывает его YAML и отдельный файл ключа.
2. Сервер запускается только после проверки provider, transport, комнаты, ключа и совместимости установленного release.
3. Панель формирует canonical `olcrtc://` Spec URI и QR. URI содержит секрет и показывается только по отдельному действию.
4. Панель Keenetic принимает URI, проверяет его локально, атомарно создаёт клиентский YAML и файл ключа, затем перезапускает клиент.
5. Клиентский сквозной тест выполняет DNS и HTTPS через `127.0.0.1:8808`. Успехом считается внешний IP VPS, а не только живой PID.

Сервер и клиент обязаны совпадать по release generation, provider, transport, room и key. Несовместимая комбинация отклоняется до изменения работающей конфигурации.

Новая упаковка использует собственные имена служб и каталогов. Она не перезаписывает `olcrtc-admin.service`, `olcrtc-server.service`, `olcrtc-server@.service`, `/etc/olcrtc`, `/var/lib/olcrtc` и старые Entware init-скрипты во время безопасной миграции. После успешного тестового переключения Web UI предлагает отдельное архивирование и точечное удаление старого Manager. Полный продуктовый контракт находится в [PRODUCT.ru.md](PRODUCT.ru.md).

## Панель VPS

Ниже приведён целевой контракт. Фактически готовые и ещё запланированные пункты отмечены в [PRODUCT.ru.md](PRODUCT.ru.md); непроставленный stable release не считается готовым продуктом.

Панель должна предоставлять:

- первый запуск с созданием администратора и случайного пароля;
- сводку IP, ОС, uptime, TLS, версии, инстансов и активных подключений;
- создание, клонирование, изменение, запуск, остановку, перезапуск и удаление инстанса;
- выбор provider и transport только из совместимых комбинаций;
- автоматическое создание комнаты, client ID, ключа и безопасных значений transport;
- расширенные поля liveness, lifecycle, DNS и параметры выбранного transport;
- проверку конфигурации до её применения и атомарный rollback при неудачном запуске;
- Spec URI, QR и подписки без повторного отображения секрета в списках и журналах;
- диагностику DNS, времени, provider, systemd, файлов, портов и последнего запуска;
- журналы сервера и панели с удалением URI, ключей, токенов и паролей;
- проверку обновлений, установку точного release и rollback;
- импорт старой установки Manager без её автоматического удаления;
- смену логина и пароля, завершение сессий и настройку TLS;
- настройку домена и URL подписок после проверки DNS и доступности;
- опциональный зашифрованный mirror только после успешного теста хранилища.

WB Stream и удалённый Chromium показываются только на поддерживаемом Debian/Ubuntu x86_64. Неподдерживаемая функция не должна оставлять частично записанные параметры.

## Панель Keenetic

Панель должна предоставлять:

- первичную настройку даже при отсутствии `client.yaml`;
- импорт canonical Spec URI без помещения секрета в argv, URL или журнал;
- статус supervisor, дочернего процесса, SOCKS5 и последней ошибки;
- запуск, остановку и перезапуск клиента;
- изменение локальных параметров SOCKS5, liveness, lifecycle и transport в допустимых пределах;
- быструю и полную диагностику;
- сквозной тест через SOCKS5;
- безопасный просмотр журнала;
- проверку обновления, установку и rollback;
- смену пароля панели;
- локальную checksummed полную копию и восстановление с автоматическим rollback;
- позднее: скачиваемый экспорт без секрета и отдельно подтверждённый секретный экспорт.

Панель привязывается только к IPv4 интерфейса домашней сети. `0.0.0.0`, `::` и автоматическое правило WAN запрещены. Первая стабильная версия не включает TUN и не меняет маршруты всего дома.

## Безопасность

- пароль хранится только как memory-hard hash с солью;
- cookie имеет `HttpOnly`, `SameSite=Strict` и `Secure` при HTTPS;
- каждый изменяющий запрос требует сессию, CSRF и допустимый Origin;
- вход ограничен по частоте, а сессии имеют срок действия;
- backend выполняет фиксированные операции без shell-команд из запроса;
- имена инстансов, пути, URL, размеры и перечисления проверяются по allowlist;
- конфиги и ключи записываются во временные файлы с `0600/0640`, затем заменяются атомарно;
- секреты никогда не возвращаются в status API и удаляются из ошибок и журналов;
- обновление принимает только asset из строгого manifest с совпадающими repository, release, size и SHA-256;
- удаление ограничено фиксированными каталогами пакета.

## Миграция старого Manager

Панель обнаруживает старые `olcrtc-admin.service`, `olcrtc-server.service`, `/etc/olcrtc/env` и `/etc/olcrtc/key.hex`. Предпросмотр показывает только несекретные поля. После подтверждения создаётся новый инстанс, копируется ключ с безопасными правами и выполняется тестовый запуск. Старый сервер останавливается только перед финальным переключением. При ошибке новый unit останавливается, старый запускается обратно. Удаление старых файлов является отдельным действием после успешной сквозной проверки Keenetic.

На Keenetic установка также сначала обнаруживает прежнюю службу и владельца порта `8808`. Новый init-скрипт и конфигурация устанавливаются под отдельными именами и не запускаются поверх занятого порта. Переключение выполняется только после сохранения старого init-скрипта, конфигурации и PID-состояния. Неудачная сквозная проверка возвращает прежнюю службу.

## Критерий готовности релиза

Релиз нельзя объявлять готовым только по зелёному unit-тесту. Нужны установка и обновление на чистом Debian 12, установка на реальном Keenetic Entware ARM64, создание инстанса через VPS UI, импорт URI через Keenetic UI, сквозной HTTPS-тест через SOCKS5, перезагрузка обеих сторон, проверка rollback и отсутствие доступа к панели Keenetic через WAN.
